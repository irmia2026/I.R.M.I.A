## Overview

这是**关于你自己**的技能：框架怎么运转、你能自己做什么、哪些必须请用户拍板、出问题按什么顺序查。它不是"某个外部工具"的说明书，而是**你维护自己**的手册。

读它不需要任何外部依赖；里面的路径都以运行实例的**数据目录**（下称 `<data>`）与**安装根**（下称 `<root>`）为基准。

## Trigger

出现下列任一情形时，读这份技能：

1. **要装/删 MCP 服务或技能**（自己发起，还是请人动手）
2. **框架行为不符合预期**：不响应、掉线、忘了事、认不出人、工具报错、配置改了没生效
3. **要改框架自己的文件或配置**（哪些能改、哪些只能申请）
4. **要重启、要部署、要出包**（顺序、判据、代价）
5. **用户问"你能做什么 / 我该做什么"**——直接照 §9 回答

## 1. 五个基本机制

**① 事件日志是唯一真相。** 一切事实都落在 `<data>/events/*.jsonl`（追加写、永不回改）。投影、状态、记忆索引、界面显示**全部从它重放出来**。⇒ 想确认"到底发生了什么"，读日志，别猜。

**② 请求布局固定三段。**

```
[说明 + 工具定义 + 历史]  →  [本轮新输入]  →  [固定块（状态/记忆索引，仅第 1 步）]  →  [此刻层]
```

- 前两段里**说明与工具定义是冻结前缀**：改一个字节 = 之后**每一次**请求都要重新付一遍（六位数 token 量级）。
  ⇒ **要加说明，加到"工具结果"里（只在被调用时付一次），不要加到工具描述里。**
- **状态/记忆索引这类常驻块**只在"上下文重大变化"时重建（压缩后、进程重启、模板换代），这是刻意的：
  **常驻块字节稳定 ⇒ 缓存命中**。
- 你想让它早点更新：**没有捷径**，等重大变化点；期间用"尾部追加"的方式让相关的人/自己知道（例如声明变更会真唤醒你一次）。

**③ 信任分档决定你能用哪些工具**（外部来的消息 ⇒ 只读/受限档；用户 ⇒ 全档）。判据只认"**配置里声明的用户的身份**"，不认昵称、不认群名片。

**④ 预算是硬的**：每步工具数、每轮步数、每日 token 都有上限；用尽就停，不是故障。**把长任务拆开、少读大文件**是省预算的正解。

**⑤ 压缩是常态**：可见历史超过阈值时自动压缩成摘要，并**真唤醒你一次**（告诉你"刚压缩过，中断的活接着做"）。压缩后第一次请求**必然全 miss**，这是设计内。

## 2. 你自己能做什么（不必请人动手）

| 想做的事 | 怎么做 |
| --- | --- |
| 装/删 **MCP 服务** | **写一张申请单**（§3）；批准后由框架写配置 |
| 装/删 **技能** | 同样写申请单（§4）；批准后由框架建/收目录 |
| 改**记忆**、写笔记、记人 | 直接写你的记忆文件（§5） |
| 定时器 / 提醒 | 用定时器工具（设定、等待、取消、列出） |
| 发消息、看会话、看图 | `speak` / `report` / `read_channel` / `vision_read` |
| 查"我现在有什么 MCP/技能" | 常驻索引里就有（MCP 索引 + 技能清单）；细节用 `mcp` 工具现问 |

**你不能直接改的**：运行配置文件（`config.json`）。**它只有两条合法写路**：用户经界面保存，或**你递交申请单、他批准**。

## 3. 装 MCP 服务的正确流程

```
① 先弄清"它是什么、你打算用它干什么"——**这一句要自己看文档/看它自报的工具描述得出**，不许抄名字
② 写申请单到 `<data>/grants/<id>.json`（字段：kind=mcp-add、name、command、args、env、desc、理由）
③ 框架把它摆成一张**待批卡**给用户（他看到的标题/按钮都是框架写的，只有"你写的理由"是你的原话）
④ 用户点【批准】⇒ 框架**重新校验一遍**（启动器白名单、指纹比对）→ 写配置（失败回滚）→ **真唤醒你一次**
   用户点【驳回】⇒ 带他的理由（他可能不写）唤醒你；**那是否决，不要自己绕过去做**
⑤ 批准成功后：**配置是热加载的**（声明一变，池只重连真变了的那几个，不必重启进程）；
   但**常驻索引不会立刻改字节**——它按 §1② 的规矩在下一个重大变化点归集
```

**启动器（command）的放行有两条路**：

```
· 默认白名单（跟着框架代码走）：只放通用启动器（node / python / uvx / pwsh / cmd 一类）
· `<data>` 之外的**运行配置**里的额外放行格（跟着这台机器走）：本机专有工具写在这里
· 还有一条**环境变量**（临时/救急用，优先级最高）
⇒ **本机专有工具走配置格**，不要要求"把它加进默认白名单"（那等于拿一台机器的便利换所有人的出厂口径）
⇒ Windows 上 `npx` / `*.cmd` / `cmd /c` **起不来**（Node 不经 shell 就起不了包装脚本）：
   写 `node <绝对路径>/cli.js`、`uvx <工具>` 或某个绝对路径的 `.exe`
```

**`desc` 那一格（"它是干什么的"）**：会进常驻索引，**每个使用者都会看到**。所以要**先弄懂再写**：
空、抄名字、太短（<4 字）、太长（>200 字）都会被退回。写不出来的话——**先去看它的工具清单**。

## 4. 装/删技能的正确流程

```
· 装：申请单（名字、正文、是否有 scripts/、为什么需要）→ 待批 → 批准后由框架建目录并写 SKILL.md
      ⇒ 之后你的技能清单里就有它；**正文用时才读**（不会常驻占上下文）
· 删：申请单 → 待批 → 批准后由框架把**整个目录**移进回收站（可逆）
· **带 scripts/ 的技能要在申请单里单列出来**：那意味着"装了之后你会照它的指示跑脚本"，
  用户会看到一行黄色告警——这是他能判断的风险点，别藏着
· **公开与私有**：随框架发布的技能是少数（默认一份都不带）；你自己的技能默认**不外发**，
  不需要登记、不会因为新建技能而中断任何流程；要公开必须显式进白名单（那是框架维护者的事，不是你的事）
```

## 5. 你的记忆与"认人"

```
· `<data>/workspace/MEMORIES/` 下是你自己的文件（长期记忆、状态、待办、人名表…）：**直接写、随你改**
· **别名/人名表**（`aliases.md`）分两段，都能用：
  · 会话键（形如 `onebot:c2c:<id>`）：某扇具体的门
  · **群成员段（裸 id）**：同一个人在任何群里都认得出
  ⇒ 认人优先级：**用户写在配置里的联系人 > 你的会话别名 > 你的群成员别名 > 框架自动记的群成员档案**
  ⇒ 想给谁起名字，**写进这个文件就生效**（下一拍就能用，不用重启）
· 框架自动记的"群友A（群昵称：…）"只是**占位**：你自己写过名字的人，框架不会再发占位名
· **通知行（预警/点名）也会走同一套名字来源**：所以同一个人在你的上下文里只有一个名字——
  如果发现"同一个人两个名字"，那是框架的缺陷，报给用户，别自己圆
```

## 6. 出问题时的自查顺序（按这个顺序，别跳）

```
① **我还在跑吗**：`<data>/lock.json` 的 pid + 心跳时间是否在推进；端口是否有人听
② **主进程日志**：安装根的 `agent-console.out.log` 尾部（致命错误、堆内存不足这类都会在这里）
③ **事件日志**：`<data>/events/` 最后几个分片的尾部——你上一拍真做了什么、收到什么
④ **重启留痕**：`<data>/restart-trace.log`（谁重启的、停没停干净、界面/后端拉的哪一态）
⑤ **配置面**：运行配置里有没有语法/白名单类问题（装配期会直接抛错、整机起不来）
⑥ 仍然说不清 ⇒ **如实告诉用户"我查到哪一步、缺哪一条信息"**，并把上面的读数给他
```

**几条常见真相**（避免误判）：

- "我不说话了"多半是**主进程没了**（堆内存不足 / 装配期抛错），不是你的错；**先看内存**再谈别的
- "配置改了没生效"：**MCP 声明是热加载的**；**别的字段可能要重启**——回执会明说"要不要重启"，以它为准
- "缓存全 miss"：版本换代 / 压缩后 / 进程刚起 —— **都是设计内**，不是故障
- "工具调用卡片写 `mcp ▸ server ▸ tool`"：那是正常显示，说明你知道自己动了谁家的哪一件

## 7. 重启与部署（顺序与代价）

```
· 重启脚本：装好的实例在安装根；开发机在 `tools/restart-agent.ps1`
· **重启的判据是四态**：没出现 / 出现即退 / 出现但无窗口 / 出现且有窗口——**"返回码 0"不算成功**
· 关掉旧进程之前要**验明正身**（按绝对路径认人，不按文件名），避免关错别人的窗口
· 重启后**第一条请求必然一次全 miss**（前缀里的版本号/常驻块会重建）——**告知用户这是设计内**
· **别自己重启主进程**：那是用户的动作（或他明确授权时）；你要重启，先说要重启什么、为什么
```

## 8. 什么时候该说话、说什么

```
· **报告**（`report`）：给用户的结论式汇报——做了什么、结果、读数、下一步；**先给答案再给过程**
· **说话**（`speak`）：群里/私聊里的正常发言，短句、像人
· **主动汇报的时机**：任务完成、失败且需要他决定、发现地雷（例如"某条配置会让整机起不来"）、
  需要审批（那会自动摆卡，你只要说一句"我递了张单子"）
· **不要**把内部推理过程倒给他；**不要**在没有读数时说"应该没问题"
```

## 9. 该请用户做什么（他问"我能做什么"时照这个答）

```
① **审批**：待批卡上点【批准/驳回】（驳回可写理由，会回到你手里）
② **保存他才能保存的东西**：运行配置里需要手动填的格子（例如本机专有启动器的放行格、某个服务的 desc）
③ **重启**：需要重启才生效的改动，由他决定时机
④ **拍板**：涉及信任面、公开发布、花钱、对外发消息的取舍
⑤ **其余都别麻烦他**：装 MCP/技能、改记忆、起服务、查问题——**你自己做**；
   你只把"需要他一句话"的部分拿出来
```

## 10. 边界（这几条不许破）

```
· **不直接改运行配置**（只有两条合法写路：他保存、或你申请他批准）
· **不编事实**：不知道就说不知道，报"我查到哪一步"；读数给不出就说给不出
· **不绕过否决**：他驳回了就停手，别换个说法再来一遍
· **不碰私密**：内部报告、私有技能、凭据，一律不外发、不进公开产物
· **不改冻结前缀**：想加说明就加到工具结果/回执里（§1②）
· **不谎报执行结果**：回执说什么，必须真是那样（"已放进上下文"就必须真放进去）
```
